# [ADR] 退会（アカウント削除・PII 消去）機能の設計方針

* **Status**: Accepted（8つの設計軸すべて確定。実装計画・PR分割は本ADRの外で扱う）
* **Date**: 2026-07-19
* **Issue**: #180
* **観点の優先順位**: ユーザー体験 → DB 設計の保守性 → テスト容易性 → その他（この順に優先）
  * この順位は本ADRの**唯一の判断軸**である。各節の推奨は必ず優先度の高い順（ユーザー体験から）に理由を述べ、ユーザー体験で差がつかない軸のみ DB 設計で判断する。
  * 「既存実装を流用できて安い」「今の実装で可能か」は**判断軸にしない**。設計はあるべき体験から決め、実装可否や PR 分割は設計確定後のタスク分解で扱う。

## 0. 概要

### 0.1 実現したい退会体験（結論）

退会は「本人の痕跡を消せること」と「他の人の貢献を壊さないこと」を両立させる。

- **消える**: メール・パスワード等の認証情報と表示名（PII）は即時・不可逆に物理削除。本人しか触れていない投稿——**まだ誰もアドバイスしていない相談**と下書き——も物理削除（非表示にするのではなく消す）。
- **匿名で残る**: **アドバイスが付いた相談**と、本人が他人に書いたアドバイスは、著者名を伏せて「退会済みユーザー」として残る（他者のアドバイスとスレッドの文脈を守るため）。
- **再登録できる**: 退会後、同じメールアドレスで再び登録できる（過去の投稿とは結びつかない、まっさらな新規アカウントになる）。
- **操作と誤操作防止**: 設定画面から本人が開始し、確認ダイアログ＋type-to-confirm（メール入力）＋「◯件削除／◯件匿名化」の明示で誤操作を防ぐ（パスワード再入力は求めない）。
- **例外なく行使できる**: 無効化（BAN）中でも退会（消去権）は行える。

この体験は、退会に関わる3者（退会者本人／回答をくれた他者／後から読む閲覧者）を比較し、「全部残す」「全部消す」「全部本人に選ばせる」といった代替案（§4）を検討した上での結論である。

### 0.2 判断の優先順位（評価観点）

- **ユーザー体験（最優先）**: 退会に関わるのは退会者本人だけではない。次の**3者すべて**が実在ユーザーであり、その体験を天秤にかける（詳細 §4.2）。
  - 退会者本人 … 自分の痕跡・PII を消したい
  - アドバイスをくれた他者 … 自分の回答を巻き添えで消されたくない
  - 閲覧者（同じ悩みを持つ将来のユーザー）… 参考になったスレッドを失いたくない
- **DB 保守性（第2軸）**: ユーザー体験で差がつかない軸を判断する。**必要があれば列・テーブルは足す**——保守性とは「列数の少なさ」ではない。避けたいのは、必要性に見合わない複雑さと、**常に整合を取り続けねばならない状態**（例: `deletedAt` を立てる＋`name` を伏せ字化する二重表現の同期）や、**全クエリで守り続けねばならない不変条件**（例: `deletedAt` を全所で除外し忘れると消したはずのユーザーが漏れる）。ユーザー体験の価値が同じなら、この継続的な負債が小さい方を採る。
- **テスト容易性（第3軸）**: 削除処理の順序や、途中で失敗しても再実行で正しく完了すること（何度実行しても最終結果が同じ）を、自動テスト（バックエンド単体 / API テスト・フロントのコンポーネントテスト）で検証できる形。
- **法令・プラットフォーム**: GDPR 消去権 / APPI 消去に適合すること。Apple 5.1.1(v) は「アカウント作成を提供するアプリはアプリ内退会も必須」とする App Store 審査要件で、Web のみの現状は対象外だが将来 iOS アプリを出すと必須になる（各用語は §12 参照）。
- **最終形態を見据える**: 通報/モデレーション（issue #136）、監査ログ（issue #148 / #150）の最終形まで含めて破壊的変更を避ける。

### 0.3 比較した設計軸（直交する設計軸に MECE 分解）

退会機能は単一の選択ではなく、**独立して決められる複数の軸**の組合せである。以下は issue #180 に挙がった設計判断（投稿の扱い・削除方式・content_checks・BAN との整理）を網羅し、issue 未言及の軸（タイミング・実行機構・誤操作防止）を補ったもの。

| 設計軸 | 何を決めるか |
|---|---|
| 認証情報・PII の扱い | email / password / token / セッションをどう消すか |
| 業務 users 行の扱い | 業務ユーザー行を物理削除するか、tombstone として残すか |
| 投稿（相談・アドバイス）の扱い | 匿名化して残す / 削除 / 非対称 |
| タイミング・可逆性 | 即時・不可逆 / 猶予期間 / 二段階 |
| 実行機構 | Better Auth `deleteUser` / 独自エンドポイント |
| 監査・関連レコード | content_checks / moderation_actions / 監査ログの整合 |
| 誤操作防止・確認 | 確認ダイアログ / type-to-confirm / メール確認リンク / パスワード再認証 のどれを課すか |
| BAN（無効化）との概念整理 | 退会と disabled（issue #136）をデータモデルで区別 |

### 0.4 推奨・決定サマリ

| 設計軸 | 推奨 | 判断理由 | 状態 |
|---|---|---|---|
| 認証情報・PII | **hard delete**（authUsers/sessions/accounts/verification を物理削除。実行は §5 の退会ユースケース） | 退会者の「確実に消えた」安心。消去権・APPI 消去を満たし email を再登録可能に戻す。物理削除以外に有効な選択肢がなく自明（§2） | **決定** |
| 業務 users 行 | **hard delete** | UX はほぼ同一（唯一の差は §3 の匿名著者の区別で、現状要件なし）→ DB 保守性で判断: soft delete は「全クエリで `deletedAt` を除外し続ける不変条件」＋`name` の伏せ字化の整合維持という継続負債を負う。hard delete は行が消えて状態が単純（`name`(PII)も行ごと消える） | **決定** |
| 投稿 | **非対称モデル**（他者が依存するものだけ匿名化保持。下書きと回答0件の相談は削除） | 退会者は自分のものを消せて区切りになり、他者の貢献は守られる。全保持案は消せず、全削除は他者を害す | **決定** |
| タイミング | **即時・不可逆 + 強い確認** | PII が即消える確実性。DB 保守性: スケジュール purge 不要。猶予期間は主に課金/再engagement目的で本プロダクトの退会意図と噛み合わない | **決定** |
| 実行機構 | **退会ユースケースで原子的に削除（Better Auth のフック/deleteUser は使わない）** | 全削除を1つの db.batch にまとめ原子的（部分失敗なし）。処理をユースケース層に集約し auth.ts を肥大させない。BAN 中でも退会可（§5.5） | **決定** |
| 監査・関連レコード | 退会を**誰でもブロックしない**。content_checks は対象に追従、moderation_actions の実行者は **PII を含まない写し**で保持 | 管理者も消去権を持つ。監査は退会で壊れず PII も残さない（§6） | **決定** |
| 誤操作防止・確認 | **確認ダイアログ + type-to-confirm（メール入力）+ 削除/匿名化件数の明示**（パスワード不要。CSRF は退会 API で対策） | 「ワンクリック削除」と機械的削除を防ぐ。パスワード必須は忘却ロックアウトを招くため避ける（§5.6） | **決定** |
| BAN との概念整理 | **退会と disabled(BAN) は別状態**（§8 の表） | 混同するとデータモデルが崩れる | **決定** |

- 退会後の再登録は「同一メールで新規の未連結アカウント」で**決定**（§2）。
- 状態はすべて「決定」＝合意済み（本ADRの設計軸は確定）。

### 0.5 確定状況

**8つの設計軸はすべて決定済み**（§0.4）。将来の強化策（端末前の第三者も防ぐメール確認リンク方式・§5.6）と、前提となるパスワード忘却リセット導線は別 issue に切り出す（§10）。

> 投稿（相談・アドバイス）の扱いは §4 の UX 分析とプロダクト像（蓄積型ナレッジ Q&A・本文の PII 抑制・現状は匿名）を踏まえ **非対称モデルで合意済み**。

### 0.6 採用しなかった案（要点。詳細は各節）

- **全保持案（投稿を全部匿名化して残す）**: 退会者から「自分の投稿を消す」選択肢を完全に奪う。他者保護のための保持は**他者が関わった部分だけ**で足り、本人しか触れていない投稿まで残す理由がない。退会者の体験として劣る（§4.2）。
- **全削除（本人の投稿を無条件に全部消す）**: 回答が付いた相談を消すと**他人のアドバイスが巻き添え**になり、蓄積ナレッジも壊れる。回答者・閲覧者の体験を害す。主要 UGC で thread+返信を cascade 削除する例は存在しない（§4.5）。
- **soft delete のみで PII 物理消去しない（認証情報・PII を soft 化）**: Apple は「無効化・deactivate は不十分」と明記。GDPR/APPI も識別子の物理消去を要求（§2, §9.2）。
- **独自エンドポイントを authGuard 配下に作る**: authGuard が disabled(BAN) を 403 で弾くため、**BAN 中ユーザーが消去権を行使できなくなる**（§5.4）。

## 1. 背景

アカウント作成時に email 等の PII を保存している。本人が自分のアカウントと PII を削除できることは当たり前品質であり、MVP に必要（法令・Apple 要件・リスク低減、issue #180 参照）。

fumufumu は**相談（consultation）に他ユーザーがアドバイス（advice）を付ける、蓄積型のナレッジ Q&A**である。投稿は表示名（ハンドル）ベースの匿名投稿で、公開前に運営が投稿チェックを行う。したがって「退会者の投稿をどう扱うか」は、退会者本人だけでなく**アドバイスを書いた他者・後から読む閲覧者**の体験に影響する。ここが本設計の核心（§4）。

### 1.1 現状のデータモデル（PII の所在）

| テーブル | PII / 認証情報 | 管理 |
|---|---|---|
| `auth_users` | **email**(unique), name, image | Better Auth |
| `auth_accounts` | **password**, accessToken, refreshToken, idToken | Better Auth |
| `auth_sessions` | セッション | Better Auth |
| `auth_verifications` | identifier(=email 等), value | Better Auth |
| `users` | **name**（表示名＝PII）, disabled, role, timestamps | 業務層 |
| `auth_mappings` | authUserId ↔ appUserId の対応 | 業務層 |

`consultations` / `advices` 本文は UGC。`content_checks` / `moderation_actions` は監査系。

## 2. 認証情報・PII の扱い → hard delete（決定）

| 方式 | 退会者の安心/PII消去（UX） | 法令適合 | 再登録(email 再利用) | 保守性（DB設計） | 判定 |
|---|---|---|---|---|---|
| hard delete（物理削除） | ◎ 確実に消える | GDPR/APPI ○ | 可 | シンプル | **採用** |
| soft delete + フラグのみ | ✗ 残存 | Apple「deactivate は不十分」/GDPR ×| 不可（unique 衝突） | フラグ分岐が全所に波及 | 却下 |
| anonymize in place（値を上書き） | ○ | ○（不可逆なら） | email を空/擬似値にする必要 | 上書きロジックが必要 | 不採用（本件では利点なし） |

**採用理由**: 退会者に「認証情報・PII が確実に消えた」という体験を返せる。退会ユースケースが authUsers/sessions/accounts（+ verification token）を物理削除するため、email/password/token/セッションが確実に消える（§5）。email の unique 制約も解放され、同一メールで再登録できる。GDPR 消去・APPI 消去のいずれも明確に満たす。

選択肢は hard delete のほかに、soft delete + フラグ（却下）、anonymize in place（不採用）、および crypto-shredding がある。

- **anonymize in place（値を上書き）** の利点は「行を物理削除できない基盤（追記専用ストア・削除を拒む外部認証・削除を阻む FK 等）でも PII だけ消せる」点のみ。本件は Better Auth で確実に削除でき email も解放したいので、hard delete に対する利点がなく不採用。
- **crypto-shredding（PII を暗号化し退会時に鍵を破棄して復号不能化）** も理論上あるが、これも物理削除できない基盤（イミュータブル/イベントソーシング等）向けで、行を確実に削除でき鍵管理を増やしたくない本件では過剰。

→ 結局、物理削除以外に有効な選択肢はなく **hard delete が自明**。

**再登録の扱い（決定）**: hard delete で email の unique 制約が解放されるため、退会後に同じメールで再登録できる。ただしそれは**過去の投稿とは結びつかない、まっさらな新規アカウント**（新しい `users.id`）になる——退会で業務 `users` 行も対応表 `auth_mappings` も消えており、旧アカウントへ再連結する手段はない（連結できたら消去の意味がない）。

## 3. 業務 users 行の扱い → hard delete（決定）

**UX は実質同一**（残す投稿はいずれも「退会済みユーザー」表示、退会者の PII はいずれも消える）。理論上の唯一の差は「スレッド内に複数の退会者がいるとき、匿名のまま互いを区別できるか」だが、これは **fumufumu では価値がほぼ無い**——アドバイスはフラット構造（相互参照しない）で、著者欄に要るのは「退会済み」という一情報のみ、複数退会者が同一スレに並ぶのも稀、Reddit/GitHub も単一 tombstone に collapse している。よって UX では差がつかず、DB 保守性で判断する:

| 優先軸 | 観点 | hard delete（推奨） | soft delete（tombstone 保持） |
|---|---|---|---|
| UX | 残す投稿の表示 | 「退会済みユーザー」 | 「退会済みユーザー」 |
| UX | 複数退会者の区別（fumufumu では価値ほぼ無し） | 不可（全員 null に collapse し同一表示） | 可能（tombstone ごとに別）だが上記の通り実益は乏しい |
| DB設計 | `users.name`(PII) の消去 | 行ごと消える（自然） | `name` を明示的に伏せ字化する必要 |
| DB設計 | 維持コスト | 追加の不変条件なし | `deletedAt` を全クエリで除外し続ける不変条件 + name の伏せ字化の整合維持（列が増えること自体ではない） |
| DB設計 | 監査 `moderation_actions.adminUserId` | RESTRICT 対応が必要（§5.5） | FK 有効なまま保全 |
| テスト | テスト容易性 | ◎（状態が単純） | △（分岐・フィルタ・伏せ字化のテスト増） |

**決定 = hard delete**。UX で差がつかない以上 DB 保守性で判断すると、soft delete は「全クエリで `deletedAt` を除外し続ける不変条件」＋`name` の伏せ字化の整合維持という**継続的な負債**（列が1本増えること自体ではなく、除外を忘れると消したはずのユーザーが漏れる類の罠）を負う。hard delete は行が消えて状態が単純で、この不変条件を持たない。`users.name`(PII) も行ごと自然に消える。<br>
**soft delete を採る余地**: 「複数退会者の匿名区別」が将来はっきりした UX 要件になった場合のみ（その時は必要性ゆえに列を足せばよく、列追加自体は保守性の悪化ではない）。なお §6 の監査の実行者は PII を含まない写しで持つ方針のため、その回避のために soft delete を選ぶ必要はない。

## 4. 投稿（相談・アドバイス）の扱い → 非対称モデル（決定）

### 4.1 比較した4案

- **全保持案**: 本人の投稿を全部残し、著者だけ匿名化
- **全削除案**: 本人の投稿を無条件に全部削除
- **非対称案**（決定）: 他者が依存するものだけ匿名化保持し、それ以外（本人しか触れていない投稿）は削除
- **全選択案**: 全投稿を退会時に本人が個別選択

### 4.2 UX 第一の分析（3者の利害）

| 選択肢 | 退会者本人（UX） | 回答者（UX） | 閲覧者（UX） | 実装（DB・テスト） |
|---|---|---|---|---|
| 全保持案 | ✗ 何も消せない | ◎ | ◎ | ◎ 一律null化 |
| **非対称案** | ◎ 本人のみの投稿は消せる | ◎ 回答付きは保持 | ○ 未回答Qは失うが価値低 | △ 分岐あり |
| 全削除案 | ◎ | ✗ 回答が巻き添え | ✗ スレッドが穴 | △ |
| 全選択案 | ◎ 最大の裁量 | 選択次第で✗ | 選択次第で✗ | ✗ |

判断: **退会は本人が自分の痕跡・PII を消すための機能（消去権の趣旨）である以上、退会者は自分のものを原則消せるのが出発点。唯一の例外が「他者がその上に積み上げたもの」で、そこは他者の貢献（取り返しがつかない）を守るために匿名化保持する。** 全保持案は本人の消去欲を完全に無視し、全削除は他者を害す。全選択案は最大裁量だが、退会という感情的な場面で1件ずつ仕分けさせる負荷が高く、かつ回答付き相談の削除は他者保護のため拒否せざるを得ず選択肢の実質が限られるため、**賢い既定 + 透明な説明（非対称案）**の方が体験として上。

### 4.3 決定：非対称案の挙動と貫く原則

**原則**: 退会者は自分のものを原則すべて消せる。**唯一の例外＝「他者がその上に積み上げたもの」**だけは、他者の貢献を守るために匿名化して残す。

| 本人のコンテンツ | 退会時の扱い | 理由 |
|---|---|---|
| 公開相談・**回答あり**（他者が関わった） | **匿名化して残す**（authorId を null 化、本文は保持） | 他者の回答を守る。本文を消すと回答が意味不明になるため著者名のみ匿名化 |
| 公開相談・**回答0件**（誰も依存していない） | **削除** | 消しても誰も傷つかず、退会者の区切りになる |
| **下書き**（相談・アドバイスの、未公開の作りかけ） | **削除** | 未公開で誰にも見えず、匿名化して残す意味がない |
| 本人が**他人のスレに書いたアドバイス** | **匿名化して残す** | 相談者本人・閲覧者がスレッド文脈に依存する（Redditの`[deleted]`と同じ。消せる leaf ではない） |

- 「回答あり」の判定 = その相談に**公開・非 hidden の advice が1件以上**存在すること（判定の厳密な定義は実装時に確定。draft/hidden/著者が既に退会済み(null)の advice の扱いを含む）。
- **透明性（UX 要件・§5.6 の誤操作防止と連動）**: 退会確認画面で「◯件は完全に削除／◯件は他の方の回答を守るため匿名化して残ります」と件数を明示する（中立文言）。

### 4.4 fumufumu の位置づけと本文センシティビティ（非対称案を支える固有事情）

- **蓄積型ナレッジ Q&A**: 後から読まれる前提のため、回答付きスレッドの保全価値が高い（非対称案の「回答あり→保持」を支持）。一方で回答0件の相談は author 離脱後に育つ見込みが低く、削除して本人の区切りになる便益（退会者の UX）が上回る。
- **本文への PII 記載は抑制する方針**: 相談・アドバイスは匿名で行い、**投稿チェック機能**が「明らかな個人情報を含む投稿を公開前に止める」役割も担う。残す匿名投稿の残存 PII リスクは低く、**本文からの個人情報の除去は不要**。
- **退会者の懸念の緩和**: ハンドル＋email＋認証情報は完全消去され、残るのは PII 抑制前提の匿名本文のみ。本人しか触れていない投稿（未回答・下書き）は削除されるため、区切りも得られる。

### 4.5 業界の非対称パターン（検証済み・非対称案の裏付け）

thread に他者が返信する構造では、いずれも「**他者が依存するコンテンツは保持、依存の無いものは本人が削除可**」の非対称で解いている。cascade 削除する主要プラットフォームは存在しない。

- Stack Overflow: **回答が付いた質問は本人でも削除不可**（＝非対称案の「回答あり→保持」）、回答0の質問は削除可（＝「回答0→削除可」）。
- Reddit: 投稿・コメントは `[deleted]` で匿名化保持、退会前に個別削除も可。
- GitHub: 他人の repo 上の issue/PR/コメントは `ghost` user に付け替えて保持。
- Discourse（相談アプリに最も近い）: Delete は「会話に穴を空け他人の返信を消す最終手段」、**Anonymize（PII を除去し投稿は保持）を推奨**。

### 4.6 将来拡張

- **平常時の個別削除機能（全選択案 相当）**: 退会に限らず、いつでも本人が自分の投稿を削除できる一般機能。非対称案（退会時の自動既定）と両立し、上乗せで裁量を高める。回答付き相談の削除可否は SO 同様のルールを踏襲。
- 「すでに公開済みで本人的に問題ない PII」の扱いも将来の考慮事項。

### 4.7 法的補足（確認事項・判断軸ではない）

- GDPR 厳格解釈では「識別子を消しても本人記述の自己特定的本文を残す」のは完全消去と言えない場合がある（EDPB 2025 CEF 報告）。fumufumu は本文 PII 抑制＋投稿チェック前提のため残存する自己特定情報は原則少ない。
- APPI の「消去」は「特定の個人を識別できないようにすること等を含む」とより緩く、著者リンクを断てば実務上満たしやすい。
- 対応: 「非対称案 ＋ 本文 PII 抑制 ＋ プライバシーポリシー明記」で運用し、将来の平常時個別削除を緩和策として持つ。

## 5. 実行機構 → 退会ユースケースで原子的に削除（決定）

### 5.1 方針（Better Auth のフック/deleteUser は使わない）

退会は**普通のユースケース（サービス＋ハンドラ）1箇所に集約**して実装する。Better Auth の `deleteUser` も、そのフック（`beforeDelete` / `afterDelete`）も**使わない**。

- 読みやすさ・保守性: フックは `auth.ts`（Better Auth 設定）に処理を書くことになり肥大させ、処理がユースケース層から分断されて**フックの存在を知らないと読み逃す**。退会という重要処理を隠れた場所に置かない。
- エラー堅牢性: 認証テーブルも業務テーブルも**すべて我々の Drizzle スキーマ（`schema/auth.ts` ほか）で定義した自分たちのテーブル**で、同じ D1 の中にある。だから削除を**1つの `db.batch`（D1 では原子的トランザクション）にまとめられ**、全部成功か全部取り消しかになる（部分削除が起きない。§5.3）。
- 誤操作防止は確認ダイアログ＋type-to-confirm（§5.6）で行い、**パスワード再認証は採らない**ので Better Auth の再認証機構も不要。`auth.ts` は現状のまま。

### 5.2 フロー

```
DELETE /api/users/me （退会ユースケース。認証必須。ただし BAN 中でも通す＝§5.5）
  1. 誤操作防止: 確認ダイアログ＋type-to-confirm（メール入力）で意図を確認（パスワードは要求しない。§5.6）
  2. セッションの authUserId → appUserId を auth_mappings（対応表）から取得
  3. 削除/匿名化の件数を数える（確認ダイアログの「◯件削除／◯件匿名化」表示用）
  4. 1つの db.batch（原子的）で:
       - 下書きの相談・アドバイス ＋ 紐づく content_checks を削除
       - 回答0件の公開相談 ＋ content_checks を削除
       - 回答ありの公開相談 / 本人のアドバイス → authorId を null 化（匿名化保持）
       - users 行・auth_mappings を削除
       - auth_sessions / auth_accounts / auth_users を削除、auth_verifications（email 一致分）を削除
       - 退会イベントをログ（PII なし）
  5. セッション cookie をクリアして完了を返す
```

- すべてを1つの `db.batch` に入れるので削除は**原子的（全成功か全ロールバック）**。`authorId` の `set null` FK は最終防御として残しつつ、削除/null化はコードで明示して意図を可視化する。

### 5.3 D1 の前提とエラーハンドリング（原子化で単純になる）

- D1 は外部キーを**既定で強制**（`set null` / `cascade` がランタイムで発火）。**Workers ランタイムでは `db.transaction()` が使えない**（`BEGIN TRANSACTION` がエラー）ため、複数文を原子的に実行するには **`db.batch([...])`** を使う——`db.batch` は D1 では**1つの原子的トランザクション**で、途中失敗なら全体ロールバック。退会の全削除はこの1バッチにまとめる。
  - 補足: `scripts/tags.ts` の `db.transaction()` は別物（`better-sqlite3` でローカルの D1 ファイルを直接開くオフラインスクリプト）。ランタイム経路の制約とは無関係。
- **失敗時**: `db.batch` が全ロールバック → **何も消えていない元の状態**に戻る。ユーザーには「退会に失敗しました。もう一度お試しください」を返すだけ。
- **中途半端な部分削除（業務は消えたが認証側の機微 PII が残る等）は構造的に起きない**。これが Better Auth の `deleteUser`（内部で順番に消すだけで途中失敗が起こり得る）を使わず、自前の原子的削除（全部成功か全部取り消し）にする最大の理由。背景リコンサイル（孤児掃除の定期ジョブ）や複雑な再実行ロジックは不要。

### 5.4 将来の認証テーブル追加への備え（完全性テスト）

- 自前削除の弱点は「削除対象テーブルの一覧」を我々が維持すること。将来 Better Auth プラグイン（2FA・パスキー等）で認証テーブルが増え、削除に足し忘れると**気づかない恒久的な PII 残存**になり得る。
- 対策: **退会後にどのテーブルにもそのユーザーの行が残っていないことを検証するテスト**を置く（全テーブルを走査し当該ユーザー由来の行が0であることを確認）。足し忘れれば **CI が落ちる**ので、沈黙する恒久リークを設計時点で防ぐ。これで自前削除の唯一の弱点をほぼ無力化できる。

### 5.5 BAN 中でも退会できるようにする（消去権・UX/法令）

- 通常の `authGuard` は disabled(BAN) を 403 で弾く（`authGuard.middleware.ts:60`）。退会を単純にその配下へ置くと**BAN 中のユーザーが消去権を行使できない**（法的に不適切）。
- 対策: 退会エンドポイントは**セッション認証は必須だが disabled の 403 ゲートは適用しない**（authGuard の disabled チェックを外した専用の認証を使う）。これで BAN 中でも退会できる。
- 削除でセッション行も消えるため、以後のリクエストは自然に認証失敗になる。他端末に残る署名済み cookie は cookieCache（7 日）の期限まで有効に見え得るが、authGuard は毎回 `auth_mappings` を DB 参照する（`authGuard.middleware.ts:37-46`）ので、対応表が消えた退会済みユーザーは**次リクエストで 401** になり実害は小さい。

### 5.6 誤操作防止・確認（決定）

退会は不可逆で、PII を消し投稿の一部を削除する重い操作なので、実行前に**確認ゲート**を置く。ただし**パスワード再認証は採らない**——永続ログインでパスワードを覚えていない人が「ログイン中なのに退会できない（＝消去権を行使できない）」という本末転倒を避けるため。

- **確認ダイアログ ＋ type-to-confirm（自分のメールアドレスを入力させる）＋「◯件削除／◯件匿名化」の件数明示**。
- **CSRF 対策は退会 API の層で必須**（Origin 検証 or CSRF トークン）。本番は FE/BE 別ドメインで cookie が SameSite=none のため SameSite 頼みにできない。type-to-confirm はその上の多層防御。

**守るもの／守らないもの**（深刻度は中程度＝課金・金融なしに合わせて right-size）:
- 守る: 誤クリック、カジュアル/機械的な削除（クリックジャッキング。CSRF は API 層と併せて）。
- 守らない: 端末の前にいて本人のメールアドレスを知り得る第三者（メールは画面やログイン自動入力で露見するため type-to-confirm では防げない）。パスワード再認証なら防げるが忘却ロックアウトを招くため不採用。**この残存リスクは中程度の深刻度に照らして受容**する。
- 強化策: 端末前の第三者も防ぐ**メール確認リンク方式**（受信箱アクセスを要求・パスワード不要）を issue #185 に切り出し。パスワード再認証を将来採るなら前提として issue #186（パスワード忘却リセット導線）が要る。

## 6. 監査・関連レコード（退会をブロックしない設計）

- **content_checks**（polymorphic・FK なし・PII を持たない）: 対象コンテンツに追従する。削除する投稿の分は一緒に削除（孤児化させない）、残す投稿の分は保持。モデレーション状態のみで PII は無いため保持自体は問題なし。
- **moderation_actions.adminUserId**（`users.id` を参照する外部キー。`onDelete` 未指定＝参照先の行を消せない RESTRICT 相当。`moderation-actions.ts:19`）: この列は「その操作をした管理者は誰か」を指す。**退会者が過去に管理者としてモデレーション操作（投稿の hide/unhide）をしていると、その人を実行者として指す `moderation_actions` の行が残る**。すると退会者の `users` 行を DELETE できず（RESTRICT）、**管理者が退会できない**。
  - **決定**: 退会は誰であれブロックしない（管理者も消去権を持つ）。そのために、実行者を「**`users` 行を今も指し続ける外部キー**」で持つのをやめ、**操作時点の実行者情報の写し**（PII を含まない形。内部識別子のみを持ち、表示名などの PII は持たせない）を `moderation_actions` 自体に持たせる。こうすれば `users` 行が消えても監査記録は壊れない。issue #148 / #150 の監査ログ設計と統合する。
  - 実装メモ: 上記の `moderation_actions` 変更が MVP に間に合わない場合に限り、一時退避として管理者ロールは退会不可にしてよい（該当は運営のみで稀）。あくまで一時措置で、上記の決定に置き換える前提。
- **退会イベント自体**: PII なしで記録（誰が・いつ、本文なし）。消去権の「最小限の記録保持」に沿う。既存の `console.warn` 監査（BAN のブロックログ）と同じ粒度。

## 7. タイミング・可逆性 → 即時・不可逆（決定）

| 方式 | UX | DB 保守性 | Apple 適合 |
|---|---|---|---|
| 即時・不可逆【推奨】 | PII が即消える確実性。誤操作は確認ダイアログ＋type-to-confirm＋件数明示で防ぐ | ◎ 追加ジョブ不要 | ○（即時削除を提供） |
| 猶予期間 → purge | 誤操作/後悔を取り消せる | ✗ scheduled purge（Cron）と pending 状態管理が増える | 「即時削除も併設」が条件 |

**推奨 = 即時・不可逆 + 強い確認**。理由（UX）: 退会の主目的が「PII を消したい」である以上、猶予期間中に PII が残るのは意図と噛み合わず、PII 最小化にも反する。猶予期間は主に課金の期限合わせや再 engagement 目的の仕組みで、本プロダクトの退会意図に合わない。後悔・誤操作は確認ダイアログ＋type-to-confirm＋削除/匿名化件数の明示（§5.6）で防ぐ。将来猶予を足す場合も Apple 要件上「即時削除オプション」は残す。

## 8. BAN（無効化・issue #136）との概念整理

| | 退会（本ADR） | 無効化 / BAN（issue #136, `users.disabled`） |
|---|---|---|
| 起点 | **本人**都合 | **運営**都合 |
| 目的 | PII 消去・アカウント消滅 | アクセス遮断 |
| データ | authUsers/users を**物理削除**、投稿は削除 or 匿名化保持（非対称） | 行も PII も**残す**、`disabled=true` のみ |
| 可逆性 | 不可逆 | 可逆（admin が戻せる） |
| 認証層 | 退会ユースケース（認証は必須だが disabled ゲートは通す） | authGuard が 403（`accountDisabledBody`） |
| 表示 | 残す投稿は「退会済みユーザー」 | 投稿はそのまま（著者は生存） |

両者は**直交する別状態**。`disabled` を退会に流用しない。

## 9. 期待効果とトレードオフ

### 9.1 期待効果
- 退会者: PII が確実・即時に消え、email を再登録に使える。自分のみの投稿（未回答・下書き）は消えて区切りになる。BAN 中でも消去権を行使できる。
- 周囲（他者・閲覧者）: 回答が付いたスレッドと他者のアドバイスが巻き添え削除されず、蓄積ナレッジが保全される。
- 実装面: 退会を1つのユースケース＋1つの原子的 db.batch に集約でき、部分失敗の考慮が要らない。確認は type-to-confirm＋確認ダイアログで、パスワード再認証は使わない。

### 9.2 トレードオフ / リスク
- **匿名化保持する本文の残存**（§4.7）: GDPR 厳格解釈での残存リスク。→ 本文 PII 抑制＋投稿チェック＋ポリシー明記で緩和、将来の個別削除で更に緩和。
- **将来の認証テーブル追加時の消し忘れ**（§5.4）: 自前削除のため、Better Auth プラグイン等で認証テーブルが増えたとき削除に足し忘れると PII が残り得る。→ 退会後に全テーブルで当該ユーザーの行が0であることを検証する完全性テストで CI が落ちるようにする。
- **非対称処理の分岐コスト**（§4.3）: 「回答あり」判定・content_checks 掃除・下書き削除の分岐。DB 保守性・テスト容易性のコストだが、優先順位（ユーザー体験 ＞ DB 保守性・テスト容易性）に照らし許容。
- **cookieCache 7 日**（§5.4）: 他端末の残存 cookie。→ authGuard の mapping 再参照で実害小。

- **GDPR 消去権（第17条「忘れられる権利」）**: EU 一般データ保護規則。本人は自分の個人データの削除を請求でき、管理者は原則1か月以内（第12条(3)）に応じる。真の（不可逆な）匿名化は削除の代替になり得るが、識別子だけ消して本人を特定できる内容を残すのは不十分。 https://gdpr-info.eu/art-17-gdpr/
- **APPI（個人情報保護法）第35条**: 日本の法律。本人は一定要件で保有個人データの利用停止・消去を請求できる。「消去」は「特定の個人を識別できないようにすること等を含む」と定義され、GDPR より匿名化で満たしやすい。対応期限は「遅滞なく」。 https://www.ppc.go.jp/personalinfo/faq/APPI_QA/
- **Apple App Store Review Guideline 5.1.1(v)（アカウント削除）**: 「アカウント作成を提供するアプリは、アプリ内での退会も提供しなければならない」という審査必須要件。一時的な無効化（deactivate/disable）は代替として不可。即時削除を提供すれば猶予期間の併設は可。Web には直接かからないが、同じバックエンドで iOS アプリを出す場合に必須。 https://developer.apple.com/support/offering-account-deletion-in-your-app/ （ガイドライン本文 https://developer.apple.com/app-store/review/guidelines/ の 5.1.1(v)）
- **Better Auth `deleteUser`**: 認証ライブラリの退会機能。`user.deleteUser.enabled` で有効化し、セッション・連携アカウントを cascade 削除、before/afterDelete フックや再認証（パスワード / fresh-session / メール確認）に対応（v1.4.5 ソースで確認）。**本ADRでは不採用**（内部が順次削除で途中失敗し得る点とフック依存のため。退会は自前ユースケースで原子的に削除する。§5）。なお退会時の再認証（パスワード）も採らず、誤操作防止は type-to-confirm＋確認ダイアログで行う（§5.6）。 https://www.better-auth.com/docs/concepts/users-accounts
- **Cloudflare D1 の外部キー**: 本番 DB。FK は既定で強制され `ON DELETE SET NULL / CASCADE` はランタイムで発火する。`db.transaction()` は非対応で、複数文の原子的実行は `db.batch()` を使う。 https://developers.cloudflare.com/d1/sql-api/foreign-keys/
- **UGC の退会慣行**: 他者が返信した thread は匿名化して残し、依存の無いものは本人が削除、が業界標準（例: Stack Overflow は回答が付いた質問を本人でも削除不可）。
