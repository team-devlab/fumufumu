# 09. 退会（アカウント削除・PII 消去）実装計画

このドキュメントは **ADR 013（退会機能の設計方針・Status: Accepted）** を前提に、退会機能を小さな PR に分割して実装するための作業計画である。設計判断は ADR 013 に集約済みで、本書は「どの順で・どの単位で作るか」を扱う。

- 設計: `docs/design/adr/013-account-withdrawal-and-pii-erasure.md`
- 関連: issue #180（本件）、issue #185（メール確認リンク強化・将来）、issue #186（パスワード忘却リセット導線・前提）

---

## 1. 前提（ADR 013 で確定済みの要点）

- **認証情報・PII は物理削除**（authUsers / sessions / accounts / verification）。email の unique 制約が解放され、同一メールで**新規の未連結アカウント**として再登録できる。
- **投稿は非対称に扱う**: 他者が回答した相談・本人が他人に書いたアドバイスは **authorId を null 化して匿名化保持**、下書きと回答0件の相談は **削除**（＋紐づく content_checks も削除）。
- **実行機構は自前の退会ユースケースで原子的に削除**（Better Auth の deleteUser / フックは使わない）。全削除を1つの `db.batch`（D1 では原子的トランザクション）にまとめる → 部分失敗が起きず、エラー処理は「失敗→全ロールバック→再試行」だけ。
- **BAN 中でも退会できる**（認証は必須だが disabled の 403 ゲートは通す）。
- **誤操作防止は確認ダイアログ＋type-to-confirm（メール入力）＋件数明示**（パスワード再認証は採らない）。CSRF は退会 API で Origin/トークン検証（本番は cookie が SameSite=none のため）。
- **監査**: content_checks は対象コンテンツに追従（消す投稿の分は一緒に削除）。moderation_actions は本来「実行者を PII を含まない写しで保持」だが、この変更は issue #148/#150 と統合する。間に合わない間は**管理者ロールのみ一時的に退会不可**（該当は運営のみで稀）。
- 退会後の投稿の匿名表示（null 著者 →「退会済みユーザー」）は **既に全層で配線済み**（`consultations.authorId`/`advices.authorId` の set null、Service の `author ? {...} : null`、API 契約、フロント表示）。よって匿名化そのものに追加コードはほぼ要らない。

### スキーマ変更の要否

- **核となる退会（一般ユーザー）にマイグレーションは不要**。既存テーブル＋既存 FK（set null / cascade）で成立する。
- moderation_actions の実行者を写しに変える schema 変更は issue #148/#150 のスコープ（本計画では扱わない）。

## 2. 実装の全体像（ADR §5.2 のフロー）

```
DELETE /api/users/me （退会ユースケース。認証必須。BAN 中でも通す）
  1. 誤操作防止: 入力メールアドレスが本人のものと一致するか検証（type-to-confirm）
  2. CSRF: Origin 検証（or トークン）
  3. 管理者ロールは一時的に拒否（moderation_actions の写し化=issue #148/#150 まで）
  4. appUserId をセッション → auth_mappings（対応表）から取得
  5. 1つの db.batch（原子的）で:
       - 下書きの相談・アドバイス ＋ 紐づく content_checks を削除
       - 回答0件の公開相談 ＋ content_checks を削除
       - 回答ありの公開相談 / 本人のアドバイス → authorId を null 化
       - users 行・auth_mappings を削除
       - auth_sessions / auth_accounts / auth_users を削除、auth_verifications（email 一致分）を削除
       - 退会イベントをログ（PII なし）
  6. セッション cookie をクリアして完了を返す
```

実装時の注意（コードから読み取れない前提）:
- `authGuard`（`src/middlewares/authGuard.middleware.ts`）は disabled を 403 で弾く。退会は**その 403 ゲートを通す別の認証**が要る（authGuard から disabled チェックだけ外した派生、または専用ガード）。
- 削除は Drizzle の `db.batch([...])` を使う（D1 では `db.transaction()` は使えない）。
- 完全性テスト: 退会後、**全テーブルに当該ユーザー由来の行が残っていない**ことを検証する（将来の認証テーブル追加時の消し忘れを CI で検出するため）。

## 3. PR 分割（小さく・意味のある最小単位）

各 PR の中でも「意味のある最小単位」ごとにコミットして一旦止める（§5 の進め方に従う）。PR 間は上から順に。

### PR1: バックエンド核 — 退会エンドポイント＋PII/認証の原子的物理削除
- **ブランチ**: `feat/account-withdrawal-core`
- **やること**:
  - `DELETE /api/users/me`（退会ユースケース）を追加。認証は必須だが disabled は通す。
  - type-to-confirm（入力メールが本人のものと一致するか検証）。
  - CSRF: Origin 検証。
  - 1つの `db.batch` で users 行・auth_mappings・auth_sessions・auth_accounts・auth_users・auth_verifications を削除（この PR では**投稿は既存 FK の set null に任せて一律匿名化**）。退会イベントをログ（PII なし）。セッション cookie をクリア。
  - 管理者ロールは一時的に拒否（明示メッセージ）。
  - テスト: repository/service の単体、endpoint の API テスト（成功 / メール不一致 / BAN 中でも退会可 / 管理者は拒否）、**完全性テスト**（退会後に全テーブルで当該ユーザー行が0）。
- **Done**: 一般ユーザーが退会でき、PII・認証情報が物理削除され、投稿は「退会済みユーザー」表示になる（この時点では下書き・未回答も匿名化保持＝ADR の C-A 相当の暫定挙動）。
- **注意**: 単体でも動くが、**本番反映は PR2 まで揃えてから**（PR1 だけだと未回答・下書きも匿名化保持になり、ADR の非対称モデルと挙動が異なる）。

### PR2: バックエンド — 投稿の非対称処理＋退会プレビュー件数
- **ブランチ**: `feat/account-withdrawal-content-policy`
- **やること**:
  - PR1 の「一律 set null」を**非対称処理**に差し替え: 下書き（相談・アドバイス）と回答0件の公開相談を削除（＋紐づく content_checks を削除）、回答ありの公開相談・本人のアドバイスは authorId を null 化。すべて同じ `db.batch` 内で原子的に。
  - 「回答あり」の判定を明確に定義（公開・非 hidden の advice が1件以上、等。draft/hidden/著者退会済みの扱いを含む）。
  - **退会プレビュー**（`GET`）: 削除件数 / 匿名化件数を返す（フロントの「◯件削除／◯件匿名化」表示用）。
  - テスト: 分岐（下書き / 回答0 / 回答あり）ごと、content_checks の追従、プレビュー件数。
- **Done**: ADR の非対称モデル（C-B）どおりに削除・匿名化が分岐し、件数を事前に取得できる。

### PR3: フロント — 退会導線と確認 UI
- **ブランチ**: `feat/account-withdrawal-ui`
- **やること**:
  - 退会導線を設置（プロフィール / 設定。既存のユーザーメニュー・`(main)/user` あたり）。
  - 確認ダイアログ ＋ type-to-confirm（メール入力）＋ プレビュー件数の明示（「◯件は完全に削除／◯件は他の方の回答を守るため匿名化して残ります」）。文言は中立（「退会」で統一。「削除」等の表現は投稿チェック文言規約に準拠）。
  - 退会成功後: サインアウト相当の後処理＋リダイレクト。
  - 可能な限りサーバーコンポーネント / イベントハンドラで完結（CLAUDE.md の `useEffect` 既定禁止）。
  - コミット前に触ったフロントファイルへ biome。
- **Done**: ユーザーが画面から安全に退会でき、何が消え何が残るかが事前に分かる。

### PR4: ドキュメント — ポリシーと確認手順
- **ブランチ**: `docs/account-withdrawal-runbook`
- **やること**:
  - プライバシーポリシーに追記（消去対象 / 匿名化して残す対象 / バックアップは一定期間後に上書き消滅する旨 / 不可逆）。
  - `docs/verification/` に手動・結合テスト手順（PII 消滅・セッション失効・下書き/回答0の削除・回答ありの匿名化・content_checks 追従・BAN 中退会・件数明示）。
- **Done**: 運用と検証の手順が残る。PR3 に統合してもよい。

### スコープ外（別 issue）
- issue #185: 退会確認をメール確認リンク方式に強化（端末前の第三者も防ぐ）。
- issue #186: パスワード忘却リセット導線（パスワード再認証を将来採るなら前提）。

## 5. 進め方（実装セッション共通のルール）

- 一度に多くを変えない。**スモールステップで少しずつコミットし、動作確認しながら**進める。
- 実装が一区切り（意味のある「最小の」単位）ついたら、**コミットメッセージを作成して一旦止める**。人間がレビューする。
- コミットメッセージは**日本語**、**なぜこうしたのか**を**簡潔な箇条書き**で。読者に不要な時系列や、どこにも残らない記号は書かない。
- コミット scope の先頭に環境 prefix（be / fe / infra / ci）。例: `feat(be/user): ...`。
- フロントは触ったファイルにコミット前 biome。
- 設計・実装で気になること・確認したいこと・指摘があれば遠慮なく質問する。
- remote D1 / deploy 等の本番操作は**提案のみ**。実行は本人。
- 番号参照は `issue #NNN` / `PR #NNN` と種別を明記（裸の `#NNN` は使わない）。

## 6. 別セッションでの実装開始（推奨）

設計は ADR 013 に集約済みなので、**実装は新しいセッションで開始することを推奨**する（この長い設計スレッドの文脈を持ち込まず、ADR と本計画だけを参照する方が軽く正確）。PR1 から順に、1 PR = 1 セッション（または PR1+PR2 をまとめて1セッション）が扱いやすい。

### 実装セッションの起動プロンプト（例・PR1 用）

```
ADR 013（docs/design/adr/013-account-withdrawal-and-pii-erasure.md）と実装計画
（docs/projects/09-account-withdrawal-implementation.md）を読んで、退会機能の PR1
（feat/account-withdrawal-core）を実装してください。

- 計画 §3 の PR1 スコープだけを対象にする（PR2 以降には手を出さない）。
- スモールステップで進める: 意味のある最小単位ごとに日本語のコミットメッセージ（なぜを簡潔な
  箇条書き）を作成し、一旦止めて私のレビューを待つ。勝手に先へ進めない。
- コミット scope に be prefix。フロントを触ったら commit 前に biome。
- remote D1 / deploy は提案のみ、実行は私。
- 設計・実装で確認したいこと・気になること・指摘があれば遠慮なく質問して。
- 不可逆削除・原子性(db.batch)・CSRF・完全性テストは特に慎重に。
```

（PR2 以降は「PR1 用」の PR 名・ブランチ名・スコープを置き換えて同様に。）
